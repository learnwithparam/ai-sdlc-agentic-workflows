Notes on the git numbers:

- The "P- commits" filter uses `--grep=^P-`, which matches any line of a message. Here it matches only the 3 subjects `P-1`, `P-2` and `P-3`. To check: `git log --format='%h %s' --grep=^P- 52122d2`. The `A-1` commits from the postmortem fix are not P- commits, so they are not counted.
- The range has no binary files, so numstat has no `-` rows to treat as 0.
- 9 of the 29 sized commits change 1 line. They are mostly `approve:` commits that add one row to `work/approvals.jsonl`. These commits pull the median down, so 16 lines describes the mix of commits, not a typical code change.
- The trailer share counts every commit in the range. That includes the root commit and the 11 `approve:` commits, which people made and which have no trailer.

## What these numbers do not prove

**A comparison with DORA.** The change failure rate of 13.0% falls between the "high" (10%) and "medium" (15%) groups in the DORA 2023 State of DevOps report. The "elite" group is at 5%. That ranking holds only if our definition matches DORA's, and it does not quite match. Here a deploy counts as failed only if a row in `incidents.csv` names it. DORA also counts deploys that needed a rollback, hotfix or patch without a formal incident. A rollback with no incident would never appear in this file. So 13.0% is a floor on the true rate. Also, DORA defines its groups from survey answers in ranges, and 9 failures out of 69 is a small sample: one more incident would raise the rate to 14.5%.

**What one feature cannot show.**

- **No comparison.** There is one feature and no baseline. Nothing tells us whether 27.5 h from intent to spec, 0 spec changes after the plan, or 0 files outside the plan is good, typical or lucky. Measuring that needs the same numbers for features built without this workflow, or for many features built with it.
- **The two halves never meet.** The deploy commits in `data/deploys.csv` (for example `de99423` and `afd5991`) do not exist in this repo's history. `deploys.csv` ends on 2026-10-31, before `work/rollout.yaml` was approved on 2026-11-01. This feature's own lead time, failure and restore time are not part of the DORA numbers yet.
- **Following the plan does not mean the result is correct.** "0 files outside plan.md" and "0 spec commits after the plan" show that the process held. They do not show that the code is right. The retried-wrench bug was still shipped and needed a postmortem and the `A-1` fix (`e161f69`, `7dcb13b`). None of the git measures above counts that bug as a failure.
- **A trailer does not show speed or quality.** A 60% trailer share says who is credited on the commits. It says nothing about speed, quality or how much work a person did. METR's 2025 study of experienced open-source developers found that AI tools made them about 19% slower, even though they believed the tools made them faster. Attribution and productivity are different things.
- **Elapsed time includes waiting.** Commit times are author dates, set by whoever made the commit. Intent to spec includes a night and the approval wait (`54cc768`), and it measures elapsed time, not effort.
